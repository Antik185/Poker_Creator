# AntikPoker V2.1: профили и история MTT

Дата: 2026-11-02. Ветка: `codex/antikpoker-v2-auth`.

Изменения подготовлены только локально. Push, deploy, DNS, Cloudflare, Gcore и Nginx не изменялись.
История отдельных раздач не реализовывалась.

## Реализовано

- Профиль: просмотр, предварительный просмотр, загрузка, замена и удаление аватара.
- Логин и аватар аккаунта используются сервером при входе в лобби, регистрации MTT и посадке.
- Авторизованный пользователь не может выбрать гостя: проверяется HTTP API и Socket.IO, а не только кнопка.
- Анонимный пользователь выбирает вход в аккаунт или гостевую игру. Гостю выдаётся `Guest########` и стандартный аватар.
- Гостевой идентификатор связан с подписанной cookie и SQLite. Обновление страницы и перезапуск сервера сохраняют его имя, место и стек.
- Аккаунт получает постоянный игровой UUID, уникальный по `user_id`. Второе устройство возвращается на то же место; старый сокет теряет управление.
- Результаты участия через аккаунт в запланированных MTT сохраняются в SQLite, выводятся в профиле с пагинацией и статистикой.
- Аватар обновляется у уже сидящего игрока без пересоздания места. Оформление комнаты, GIF и реакции не заменяются.

## Правила смены сессии

Выбран консервативный переход: вход или регистрация аккаунта в браузере с активным гостевым участием возвращают HTTP 409 с объяснением. Сначала нужно завершить гостевую игру/участие. Гостевое место не превращается в аккаунтное и не передаётся по совпадению имени.

Выход из аккаунта отзывает текущую сессию и отключает её игровые сокеты. Место остаётся за аккаунтом, фишки сохраняются; действуют обычные правила offline/AFK. Для возврата необходимо войти в тот же аккаунт. Другие действующие сессии того же аккаунта не отзываются кнопкой выхода из текущей сессии.

Каждый входящий пакет аккаунтного сокета проверяет сессию. Дополнительно раз в секунду проверяется срок действия, чтобы отключить истёкшую сессию даже без исходящих действий игрока. Смена сессии показывает в игре сообщение о необходимости обновить страницу.

Анонимный браузер после выхода может отдельно начать гостевое участие, но не получает управление оставленным аккаунтным местом. Это не преобразование старого места. Ограничение мультиаккаунтинга между независимыми браузерами не входит в эту задачу.

## Безопасность аватаров

- Endpoint: `POST /api/profile/avatar`, multipart-поле `avatar`; удаление: `DELETE /api/profile/avatar`.
- Требуются сессия владельца, CSRF-токен и допустимый Origin. `userId` клиента не выбирает владельца.
- Максимум 5 MiB, один файл, без дополнительных multipart-полей.
- Проверяется фактически декодируемый формат: PNG, JPEG или WebP. MIME и исходное имя не считаются доказательством типа файла.
- Лимиты: 40 миллионов входных пикселей, не более 8192 пикселей по каждой стороне, одна страница/кадр.
- `sharp` поворачивает изображение по ориентации и обрезает до 256x256 WebP; метаданные исходника не переносятся.
- Имя файла генерируется UUID. Исходный путь клиента не используется. Временные файлы скрыты; публикация выполняется переименованием.
- Старый файл удаляется после успешного сохранения ссылки в БД. При неудачном декодировании новый файл не публикуется.
- До 10 попыток изменения за час на аккаунт; параллельная обработка для одного аккаунта блокируется. Ограничитель локальный для процесса, сбрасывается при перезапуске.
- Публичный URL: `/profile-avatars/<uuid>.webp?v=<timestamp>`. Ответы профиля и истории имеют `Cache-Control: no-store`.
- Директория по умолчанию: `public/uploads/profile-avatars`; можно задать `PROFILE_AVATAR_DIR`.

`sharp` обновлён до 0.35.5 после обнаружения уязвимостей в первоначально выбранной версии. Проверка npm при установке исправленной версии: 0 уязвимостей. Для интеграционных тестов добавлен devDependency `socket.io-client`: в отличие от браузерного bundle в Node он действительно передаёт cookie при WebSocket-handshake.

## Данные и история

Миграция 2 добавляет:

| Объект | Назначение |
|---|---|
| `users.avatar_path`, `avatar_updated_at` | Текущий аватар |
| `gameplay_identities` | Постоянная ACCOUNT/GUEST identity, уникальные пользователь и гостевое имя |
| Поля `user_id`, `identity_type`, `avatar_url` регистрации MTT | Неизменяемое владение участием |
| `user_tournament_results` | История аккаунта; уникальность `(user_id, tournament_id)` |

Существующие регистрации получают тип `LEGACY`, без автоматического присвоения аккаунтам. Старые никнейм-аватары остаются для legacy-регистраций; новые ACCOUNT используют профиль, новые GUEST используют стандартный аватар.

История содержит название турнира и сообщества, время регистрации/старта/завершения, число участников, итоговое место, признак финального стола и статус `SCHEDULED / RUNNING / COMPLETED / CANCELLED`.

Регистрация создаёт запись истории сразу. При сохранении состояния MTT история синхронизируется в той же SQLite-транзакции. Место берётся из серверной регистрации, которую обновляет существующий менеджер выбываний/победителя; браузер не присылает результат. Повторная регистрация и повторное сохранение не создают дубликаты.

Финальный стол отмечается отдельным callback менеджера только после закрытия регистрации и фактической сборки единственного финального стола. Место <= 9 само по себе не считается доказательством. Старым результатам признак не выдумывается.

Удаление незавершённого турнира отмечает историю как CANCELLED. Завершённые результаты не удаляются вместе с комнатой: у истории намеренно нет каскадного FK на комнату. Гостевые результаты не присваиваются аккаунту задним числом.

API только для текущего пользователя:

- `GET /api/profile/tournaments?page=1&limit=10` (максимум 20 на страницу).
- `GET /api/profile/tournament-stats`.

Статистика считает завершённые MTT: сыграно, победы, подтверждённые финальные столы. Незавершённое участие видно в истории со статусом «Идёт», отменённые турниры не увеличивают статистику.

## Основные файлы

- `server/gameIdentity.js`: выбор аккаунтной/гостевой identity.
- `server/userAuth.js`, `server/index.js`: переходы сессии, HTTP/Socket.IO проверки, подключение маршрутов, обновление аватаров.
- `server/profileRoutes.js`: загрузки и приватные API профиля.
- `server/db.js`, `server/migrations.js`: схема, владельцы регистрации, история.
- `server/tournamentManager.js`: учёт финального стола и передача аватаров.
- `public/game-entry.js`, `.css`, `public/lobby.html`, `public/poker.js`, `.html`: выбор входа и серверное имя.
- `public/site/js/profile.js`, `auth.js`, `pages/profile.html`, `login.html`, `register.html`, `css/auth.css`, `templates/layout.html`: профиль и история.
- `server/siteRenderer.js`, `public/diagnostics.html`: версия ресурсов `20261102b`.

## Границы проверки и ограничения

- Это не production-проверка и не гарантия доступа из сетей РФ. Настройки маршрутизации не менялись. В локальном коде автоматический guest-only edge handoff пропускается для вошедшего аккаунта, чтобы не потерять аккаунтную сессию при переходе между доменами. На резервном домене аккаунт пока требует отдельного входа; общий SSO между доменами не реализован.
- Реальный Safari/iOS и Android, ручная загрузка фотографии через системный диалог и полный живой MTT с людьми ещё требуют проверки на устройствах. Серверная обработка загрузок проверена интеграционно.
- Подтверждение email, восстановление пароля, смена логина, история отдельных раздач и перенос гостевых результатов не добавлялись.
- История относится к scheduled MTT, не к обычным instant-комнатам.
- Если пользователь удалит гостевую cookie, одного совпадения имени недостаточно для восстановления места. Это защита от захвата, а не основание выдать новый доступ.
- При аварийном завершении процесса между файловой операцией и записью БД может остаться неиспользуемый файл. Автоматический сбор таких файлов не реализован; нормальная замена/удаление и ошибки обработки очищаются.
- База и каталог аватаров должны резервироваться вместе. Для нескольких экземпляров приложения нужен общий файловый storage и общий rate limiter.
- Не выкатывать отдельные промежуточные коммиты стека: схема, сервер и клиент должны быть установлены совместно. Общие hooks аккаунтов, гостей и MTT пересекаются, поэтому границы коммитов сгруппированы по зависимостям, а не строго по буквам исходного задания.

## Перед будущим выпуском

1. Не обновлять production без отдельного разрешения. Дождаться отсутствия активных игр, особенно старых комнат с payload-based identityVersion 1: доверие произвольному client playerId не сохраняется.
2. Сделать согласованный backup SQLite и uploads, проверить восстановление на отдельном каталоге.
3. Установить весь стек, зависимости через `npm ci`, сохранить секреты `PLAYER_SESSION_SECRET` и `USER_AUTH_SECRET`. Требуется Node.js 24.7+ с `crypto.argon2`.
4. На staging проверить два аккаунта и гостя: вход, аватар, регистрацию MTT, повторный вход с другого устройства, offline/reconnect, logout и итоговую историю после завершения.
5. Для отката остановить сервис и вернуть предыдущие код, зависимости и согласованный backup данных. Не удалять колонки вручную и не откатывать базу после новых игр без оценки потери новых результатов.

## Короткий ручной сценарий

1. Зарегистрировать аккаунт, открыть `/profile`, загрузить PNG/JPEG/WebP, проверить preview, сохранить, заменить, удалить.
2. Войти в лобби аккаунтом: нельзя выбирать гостя или произвольный ник; в списке и за столом видны логин/аватар.
3. В другом браузере без входа выбрать гостя. Обновить страницу, свернуть/развернуть и переподключиться: имя, место и стек не меняются.
4. Попытаться войти в аккаунт во время гостевого участия: получить понятный отказ без потери управления гостем.
5. Выйти из аккаунта за столом: управление отключается; снова войти в тот же аккаунт и вернуть своё место.
6. Завершить MTT, включая вылет офлайн-игрока: проверить места и историю каждого аккаунта, отсутствие чужой истории и дубликатов после рестарта.
