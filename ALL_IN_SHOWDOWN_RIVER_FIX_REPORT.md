# Исправление All-in Showdown до открытия River

## 1. Точная причина

В `PokerRoom` переходы между улицами планировались через общий метод `_schedule()`. Он хранил все таймеры, но не гарантировал, что для текущей раздачи и улицы существует только один таймер перехода.

При двух конкурирующих таймерах происходила следующая последовательность:

1. Первый таймер переводил `TURN` в `RIVER`, добавлял пятую карту и запускал задержку ее визуального открытия.
2. Второй старый таймер сразу выполнялся уже при состоянии `RIVER` и вызывал `endHand()` до завершения клиентской анимации River.
3. Отложенный River-таймер мог позднее снова вызвать переход уже из `SHOWDOWN`, из-за чего `endHand()` выполнялся повторно.

У `endHand()` не было ни проверки длины доски для спорного банка, ни защиты от повторной финализации конкретного `handNum`. Поэтому сервер мог преждевременно отправить `handWinners`, а клиент корректно, но слишком рано запускал финальную анимацию. Проблема была серверной, а отсутствие клиентской дедупликации усиливало визуальный эффект.

## 2. Изменения сервера

Файл: `server/gameEngine.js`.

- Добавлен единственный таймер шага раздачи `_handStepTimer`.
- `_scheduleHandStep()` отменяет предыдущий переход и запоминает ожидаемые `handNum` и `phase`.
- Устаревший callback игнорируется, если раздача, улица или состояние финализации уже изменились.
- Все переходы раздачи из `resumeAfterRestore()`, `startHand()`, `afterAction()` и `advancePhase()` переведены на `_scheduleHandStep()`.
- После последнего действия улицы `actingSeat` сразу становится `-1`, поэтому повторный клик или повторная команда не могут переносить таймер перехода.
- `advancePhase()` теперь работает только для `PREFLOP`, `FLOP`, `TURN`, `RIVER` и не может повторно завершить `SHOWDOWN`.
- `endHand()` для двух и более не сбросивших игроков требует ровно пять общих карт.
- Победа без вскрытия после fold остается немедленной и не требует River.
- `_finalizedHandNum` делает выплату, публикацию результата и запуск post-hand обработки идемпотентными.
- `_finalizedHandNum` сохраняется в snapshot. Старый snapshot в `SHOWDOWN` также распознается как уже финализированный.
- Post-hand callback дополнительно проверяет исходные `handNum` и `SHOWDOWN`.
- Событие `handWinners` теперь содержит `eventId`, `handNum`, `winnerSeatIdxs`, `winnerNames` и агрегированные по местам `awards`.
- `canSeatRaise()` единообразно проверяет право на повышение. Если ответить на повышение некому либо betting action не переоткрыт после короткого all-in, сервер отклоняет `raise`, а не превращает его в `call`.

## 3. Изменения клиента

Файл: `public/poker.js`.

- События `handWinners` принимаются только для текущего `handNum` и только в фазе `SHOWDOWN`.
- `_seenHandWinnerEvents` блокирует повторную корону, звук, анимацию фишек и надпись победителя.
- Повторная проверка выполняется после отложенного переворота River, поэтому callback старой раздачи не может показать победителя в новой.
- Сохранено ожидание завершения анимации закрытой River-карты перед показом результата.
- Для нескольких победителей разных side pots клиент показывает всех получателей и их суммы, а не одного ложного общего победителя.
- Локальный режим также запрещает спорную финализацию до пяти карт и повторную выплату одного `handNum`.
- Панель действий скрывает Raise и элементы выбора суммы, когда ни один соперник не может ответить. При нулевой сумме для уравнивания остается Check; при существующей ставке остаются Fold и Call.
- Повторная проверка выполняется непосредственно перед отправкой команды, поэтому устаревший интерфейс не может отправить скрытое повышение.

## 4. Side Pot

Алгоритм расчета комбинаций и формирования банков не переписывался. Выплаты теперь агрегируются по индексу места, а не по имени игрока. Это исключает конфликт одинаковых имен и дает клиенту точный список получателей каждого банка.

Проверен сценарий вкладов `100 / 300 / 500`:

- Main pot `300` получает игрок A.
- Side pot `400` получает игрок B.
- Последние `200` игрока C не образуют side pot: это uncalled bet, который возвращается C отдельно.
- Игрок C не публикуется как победитель банка и не получает победную корону/анимацию.
- В обратном сценарии, где C выигрывает разыгрываемые банки, C присутствует в `winnerSeatIdxs` и `awards` на `700`, а тот же игрок отдельно получает `refund` на `200`.
- Повторный `endHand()` не меняет стеки и не публикует второй результат.

## 5. Тесты

Добавлен `test-all-in-showdown.js`, подключенный к `npm test`, `npm run test:unit` и `npm run test:tournament`.

Покрыты обязательные сценарии:

1. Игрок A лидирует на Turn, River меняет победителя на игрока B.
2. All-in на Preflop: Flop, Turn и River до Showdown.
3. All-in на Flop: Turn и River до Showdown.
4. All-in на Turn: River до Showdown.
5. Математически гарантированный победитель все равно ожидает River.
6. Три игрока и разные стеки: два разыгрываемых банка плюс отдельный возврат uncalled bet.
7. Игрок одновременно выигрывает разыгрываемые банки и получает отдельный возврат uncalled bet.
8. Единственный оставшийся после fold игрок получает банк сразу.
9. Повторная команда в окне перехода улицы не принимается и не переносит таймер.
10. Два быстрых конкурирующих таймера, повторная финализация и восстановление snapshot.
11. Недоступный Raise отклоняется без изменения ставок; Call выполняется только отдельной командой.
12. Тот же guard в MTT-режиме и статические проверки клиентской защиты и панели действий.

Полный `npm test` завершен успешно. В том числе прошли multiplayer E2E `23/23`, effect E2E `9/9` и tournament E2E `14/14`; проверены Showdown, следующая раздача, elimination, завершение турнира и продолжение игры с офлайн-участниками.

Итоговая последовательность для спорной all-in раздачи:

`All-in -> оставшиеся улицы -> River -> Showdown -> единственная выплата -> завершение раздачи`.
