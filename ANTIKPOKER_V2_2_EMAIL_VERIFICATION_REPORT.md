# AntikPoker V2.2: подтверждение email

Дата: 2026-11-03. Изменения локальные, поверх V2.1.

**Deploy не выполнялся. Настройки VPS, DNS, Cloudflare, Gcore и Nginx агентом не менялись.** Пользователь настроил домен в Resend и предоставил ключ через локальный файл. Resend принял настоящее контрольное письмо на согласованный пользователем Gmail от `noreply@antikpoker.online`; получение письма подтверждено пользователем. Автотесты используют только поддельный транспорт.

## 1. Регистрация

1. `/register` запрашивает временную HttpOnly-cookie и CSRF-токен.
2. POST регистрации проверяет поля, уникальность в `users`, ограничения и сохраняет Argon2id-хеш пароля во временную заявку.
3. Сервер отправляет шестизначный код. Только после принятия письма SMTP-транспортом возвращается HTTP 202 и открывается `/verify-email`.
4. Правильный код атомарно создаёт строку `users` с `email_verified_at` и удаляет заявку в одной SQLite-транзакции.
5. Полноценная сессия не создаётся. Интерфейс показывает успешное завершение и переводит на `/login`.

До подтверждения нет строки `users`, аккаунтного userId, auth session и аккаунтной игровой identity. Доступен только обычный гостевой режим. Временная cookie регистрации не принимается как cookie авторизации.

Повторный правильный запрос после завершения не создаёт второй аккаунт. Конкурирующие заявки могут использовать один логин/email, но выигрывает только первая успешно подтверждённая: финальная проверка уникальности и INSERT выполняются внутри транзакции. Временные заявки не резервируют логин навсегда.

## 2. Временное хранилище и миграция

Миграция SQLite **3** добавляет:

- `pending_registrations`: временный ID, HMAC владельца cookie, тип REGISTER/EXISTING, данные регистрации, Argon2id-хеш, HMAC кода, сроки, число попыток/отправок, состояние доставки и безопасный returnTo.
- `email_verification_limits`: сохраняющиеся при рестарте счётчики по HMAC email и IP.

Существующие users, auth sessions, аватары, игровые места и MTT-результаты не удаляются и не перепривязываются. Пароли и коды открытым текстом в SQLite не сохраняются. Временные заявки живут час; коды — десять минут. Очистка выполняется при старте, раз в минуту и перед запросами подтверждения.

Проверка кода использует HMAC-SHA256 с отдельным `EMAIL_VERIFICATION_SECRET`, временным ID заявки и кодом; сравнение timing-safe. Секрет должен содержать не менее 32 байт и сохраняться между перезапусками. Его смена делает существующие заявки недействительными, но не затрагивает аккаунты и их пароли.

## 3. API и ограничения

| Маршрут | Назначение |
|---|---|
| GET `/api/auth/registration` | Временная cookie, CSRF и состояние заявки; email маскируется |
| POST `/api/auth/register` | Валидация, временная заявка, отправка; не создаёт users |
| POST `/api/auth/verify-email` | Подтверждение; создание нового аккаунта или подтверждение старого |
| POST `/api/auth/resend-verification` | Новый код для заявки из cookie; произвольный email запроса игнорируется |
| POST `/api/auth/cancel-registration` | Инвалидация заявки перед исправлением данных |
| POST `/api/auth/start-email-verification` | Отправка кода старому аккаунту; нужна его действующая авторизация |

Новые изменяющие маршруты требуют JSON, допустимый Origin и CSRF-токен временной сессии. Cookie `antik_registration`: HttpOnly, SameSite=Strict, Path=/, Max-Age=3600; Secure при HTTPS. Ответы не кешируются. Код не передаётся в URL, не пишется в логи и не хранится в localStorage.

Лимиты:

- Пять попыток ввода на код, включая некорректный формат.
- Первая отправка плюс максимум пять повторных на заявку.
- Не раньше 60 секунд между отправками; новый код инвалидирует предыдущий.
- Отправки: до 6 на email и до 50 на IP за час.
- Подтверждения: до 30 на email и до 100 на IP за 15 минут.
- Ошибки SMTP тоже расходуют лимиты; возможна повторная попытка через минуту.

IP-лимит выше индивидуального для пользователей за общим NAT. Это защита от обычного перебора, не замена сетевой anti-DDoS-защите. Одновременные отправки одной заявки блокируются; в БД также сохраняется lease отправки. Зависшую после рестарта отправку можно повторить после его истечения.

## 4. Почта

Рабочий локальный транспорт теперь **Resend HTTPS API**, запрос `POST https://api.resend.com/emails`, без дополнительного SDK. Соединения SMTP 465 и 587 в текущей среде обрывались до авторизации; TLS-проверки не отключались. Транспорт выбирается явно через EMAIL_TRANSPORT; автоматического перехода на другой транспорт после ошибки отправки нет, чтобы не дублировать письма. HTTP-запрос имеет таймаут 20 секунд; ошибки провайдера не раскрывают ключ или тело письма. [Resend Send Email API](https://resend.com/docs/api-reference/emails/send-email).

Добавлен Nodemailer. Порт 465 использует TLS сразу, другие порты требуют успешного STARTTLS; проверка сертификата включена, минимум TLS 1.2. Настройки соответствуют [официальной документации SMTP-транспорта](https://nodemailer.com/smtp). Письмо имеет текстовую и HTML-версии, код и ссылку на `/verify-email` **без кода в URL**. Разрешён один адрес получателя, не список SMTP-адресов.

Переменные описаны в `deploy/email.env.example`:

```text
EMAIL_TRANSPORT=resend
RESEND_API_KEY=<Resend API key с правом отправки, вне Git>
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_USER=resend
SMTP_PASSWORD=
SMTP_FROM="AntikPoker <noreply@antikpoker.online>"
EMAIL_VERIFICATION_SECRET=<отдельный криптографически случайный секрет>
PUBLIC_BASE_URL=https://antikpoker.online
```

SMTP сохранён как альтернатива: для него нужны EMAIL_TRANSPORT=smtp и API key в SMTP_PASSWORD. Параметры проверены по [документации Resend SMTP](https://resend.com/docs/send-with-smtp). Шаблон `deploy/email.env.example` не содержит секретов.

Домен пользователь уже настроил в панели Resend. Не создавать дубликат и не менять корневые MX Timeweb. Если требуется дополнительная DNS-диагностика, использовать точные записи из панели, не придумывать DKIM-ключ или региональный MX. Входящую почту Resend для этой задачи включать не требуется.

Предоставленный ключ прочитан только рядом с меткой `resend api` в указанном пользователем файле, его значение не выводилось. Он сохранён в `.env.local` как RESEND_API_KEY; Git-исключение и отсутствие этого значения в публикуемых файлах проверены. Домен должен быть подтверждён для отправки от своего адреса: [Resend Verified Domains](https://resend.com/docs/dashboard/domains/introduction).

Локальный запуск: `npm run start:local`. Настроен `http://localhost:3001/register`: порт 3000 занят другим процессом, он не изменялся. Для повторного контрольного письма, только на согласованный адрес: `npm run email:check -- <email>`. Без адреса эта команда проверяет только конфигурацию API (не выдаёт её за проверку авторизации); при SMTP проверяет соединение. Реальный API key проверяется принятием письма Resend.

Через работающий локальный HTTP endpoint проверена регистрация на специальный адрес `delivered+<метка>@resend.dev`: HTTP 202, deliveryState=SENT, auth session отсутствует. Затем тестовая заявка отменена; аккаунт для probe не создавался. Это отдельная проверка после первоначального успешного тестового письма Gmail. Локальному серверу предоставлен сетевой доступ к Resend; первый запуск в ограниченной среде отправлять не мог.

Генерация секрета: `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"`. Не публиковать вывод и не добавлять заполненный env-файл в Git. `.env` не загружается приложением автоматически: нужен systemd EnvironmentFile или явная загрузка окружения Node.

Если секрет/базовый URL отсутствуют, API подтверждения возвращает 503 с объяснением; обхода создания аккаунта нет. При отказе SMTP заявка отмечается FAILED, код не принимается, интерфейс не утверждает, что письмо отправлено. Принятие SMTP не гарантирует доставку во входящие — это нужно проверить реальным письмом и у провайдера.

Публичная DNS-проверка 2026-11-03:

- SPF: `v=spf1 include:_spf.timeweb.ru ~all`.
- MX: `mx1.timeweb.ru` (10), `mx2.timeweb.ru` (20).
- Ответ TXT для `_dmarc.antikpoker.online` не получен; наличие рабочей DMARC-политики не подтверждено.
- DKIM не проверен: selector неизвестен до выбора почтового сервиса.

Не добавлять второй SPF. Для другого отправителя согласовать существующую SPF-запись с требованиями провайдера. DKIM публиковать по выданным им selector/значению. DMARC вводить отдельно после проверки alignment SPF/DKIM, не выставлять жёсткую политику без инвентаризации действующей почты. DNS не менялся.

## 5. Старые аккаунты

В локальном `poker.db` перед работой найден **1 аккаунт, 1 без подтверждения email**. Проверка была read-only, адрес и пароль не выводились. Состояние VPS здесь не проверялось.

Старый аккаунт продолжает входить и открывать профиль. В профиле есть отправка кода и продолжение подтверждения. Адрес берётся из аккаунта, а не из POST-параметра. После правильного кода обновляется тот же пользователь — ID, аватар, места и история не меняются.

До подтверждения не создаётся новая аккаунтная игровая identity; запрещены новые посадки/участия. Авторизованный старый аккаунт не может обойти это выбором гостя. Существующее место и ACTIVE-регистрация MTT допускают reconnect и продолжение; текущая раздача не прерывается, playerAction не переписан. Рекомендуемый production-переход всё равно выполнять без активных турниров.

Подтверждение старых аккаунтов не даёт функции произвольной смены email или восстановления потерянного почтового ящика. Для такого случая нужна отдельная проверяемая процедура, а не установка email_verified_at вручную.

## 6. Тесты и интерфейс

Пройден **полный `npm test`**. В runner добавлен `test-email-verification.js`; прежние auth/profile/edge-тесты теперь проходят настоящую серверную последовательность с поддельной почтой, а не прямое создание через старый HTTP endpoint.

Проверены отсутствие users/session/account identity до кода; запрет входа/профиля; ошибки, срок и пять попыток; повтор кода; cooldown; смена кода; предел повторных отправок; отказ транспорта; две конкурирующие заявки и два одновременных подтверждения; отсутствие частичного аккаунта; очистка и рестарт; CSRF/Origin/cookie; старый аккаунт, его неизменяемый ID, запрет новой комнаты и сохранение reconnect активного места. После нового подтверждения прежние profile-тесты проверяют аватар, регистрацию MTT, приватную историю и восстановление.

Тестовый транспорт подключается только preload-файлом тестового Node-процесса. В production нет HTTP endpoint получения кода и нет runtime-флага «пропустить подтверждение». Тестовая outbox хранится только во временных каталогах тестов. Код приложения не логирует коды.

Локальный изолированный staging: отдельные БД/uploads, адрес `127.0.0.1:3202`, поддельная почта. В браузере проверены отправка формы, экран подтверждения, сохранение заявки после reload, ввод кода, сообщение об успехе и переход на login без auto-login. На эмулированной ширине 390px горизонтального переполнения и ошибок JS не обнаружено. Физические iPhone/Android не проверялись.

`npm audit --omit=dev`: **0 уязвимостей**. Node локально: 24.13.1; требуется 24.7+ с `crypto.argon2`.

## 7. Проверка настоящего письма

После получения провайдера и отдельного разрешения на серверную настройку:

1. Заполнить env вне Git; подтвердить право отправлять от `noreply@antikpoker.online` у провайдера.
2. Проверить SPF/DKIM/DMARC, outbound SMTP-порт, корректность сертификата SMTP hostname. Не отключать TLS-проверку ради подключения.
3. Запустить staging с отдельной SQLite-БД, uploads, стабильными секретами и без test preload/NODE_OPTIONS. Не использовать production-базу.
4. Открыть register, ввести свой реально доступный тестовый адрес. До ввода кода проверить `SELECT COUNT(*) FROM users` в staging.
5. Проверить письмо во входящих/спаме и заголовки Authentication-Results. Убедиться, что SPF/DKIM/DMARC проходят для выбранного отправителя.
6. Ввести код; проверить появление одного users с email_verified_at, отсутствие auto-login. Затем войти, загрузить аватар и пройти тестовый MTT двумя устройствами и гостем.
7. Повторить неверный/просроченный код, resend и исправление адреса. Реальные письма отправлять только на свои/согласованные адреса.

## 8. Staging и будущий deploy

**Следующие команды — инструкция, они не выполнялись на VPS.** В прошлой диагностике известны `/var/www/poker-room` и `poker-room.service`, но актуальность пути, пользователя и EnvironmentFile необходимо подтвердить. На VPS ранее отсутствовал `.git`: не использовать вслепую `git pull`.

Перед установкой согласовать точный release-артефакт со всеми новыми файлами и lockfile. Не переносить локальные `poker.db*`, uploads, `.env*`, node_modules или тестовую outbox. Текущие изменения пока локальные; артефакт не публиковался.

Безопасные preflight-команды на VPS:

```sh
node -p 'process.version'
sudo systemctl show poker-room.service -p WorkingDirectory -p User -p ExecStart -p EnvironmentFiles --no-pager
sudo nginx -t
curl --fail --max-time 10 http://127.0.0.1:3000/healthz
```

Не выводить `systemctl ... Environment` с секретами. Точный список активных турниров проверить в админке; один `rooms` из healthz не доказывает отсутствие играющих людей.

Для staging распаковать утверждённый артефакт в отдельный каталог `/var/www/antikpoker-staging-v22`, выполнить `npm ci` **там**, задать окружение, например в `/etc/antikpoker/staging-v22.env` с правами 0600:

```text
NODE_ENV=production
HOST=127.0.0.1
PORT=3202
POKER_DB_PATH=/var/lib/antikpoker-staging-v22/poker.db
PROFILE_AVATAR_DIR=/var/lib/antikpoker-staging-v22/profile-avatars
PUBLIC_BASE_URL=https://<согласованный-staging-host>
```

Добавить SMTP/EMAIL_VERIFICATION_SECRET, отдельные staging PLAYER_SESSION_SECRET/USER_AUTH_SECRET и ADMIN_PASSWORD. Владельцу процесса нужны права на каталог БД и uploads. Для старта в foreground без изменения production-unit:

```sh
cd /var/www/antikpoker-staging-v22
node --env-file=/etc/antikpoker/staging-v22.env server/index.js
```

Публикация staging hostname/HTTPS — отдельное действие после согласования; до этого допустим SSH port-forward для локальной проверки. Не публиковать порт Node во внешнюю сеть. Для Secure cookies production-проверку провести через HTTPS и согласованную proxy-топологию.

Для production, **только после разрешения**:

1. Остановить новые регистрации турниров организационно и дождаться завершения активных игр. Не выгонять игроков обновлением.
2. Остановить `poker-room.service`; до замены старого кода сделать backup старой версией `scripts/backup-runtime.js`, проверить через `scripts/verify-backup.js`. Backup содержит персональные данные, Argon2-хеши и после V2.2 временные заявки: хранить с ограниченным доступом.
3. Сохранить старый release и systemd/environment конфигурацию. Не менять существующие SESSION_SECRET. Пользовательские uploads и БД не затирать содержимым артефакта.
4. Установить утверждённые файлы V2.2 и выполнить `npm ci`. Добавить защищённый env-файл через существующий EnvironmentFile либо согласованный systemd drop-in. Не класть секреты в репозиторий.
5. Запустить сервис: миграция 3 применяется автоматически. Проверить journal без вывода секретов, `/healthz`, `/diagnostics`, auth, register/verify, профиль, админку, polling и WebSocket.

Шаблон команд для default runtime-путей, **сначала сверить их с unit**:

```sh
cd /var/www/poker-room
sudo systemctl stop poker-room.service
node scripts/backup-runtime.js /var/backups/antikpoker-v22
# Команда выше печатает конкретный BACKUP_DIR. Использовать именно его:
node scripts/verify-backup.js "$BACKUP_DIR"
# Здесь установка согласованного release, npm ci и env; не git pull без репозитория.
sudo systemctl start poker-room.service
sudo systemctl is-active poker-room.service
curl --fail --max-time 10 http://127.0.0.1:3000/healthz
```

Если задан нестандартный `POKER_DB_PATH`, backup-команду выполнять с **тем же** окружением. `PROFILE_AVATAR_DIR` вне public/uploads резервировать дополнительно: текущий backup-скрипт копирует public/uploads, а не произвольный внешний каталог.

В прокси/CDN не кешировать `/api/auth/*`, `/api/profile/*`, verify/register/login/profile и realtime. Сохранять Host, правильный X-Forwarded-Proto и cookie; Secure-cookie требует, чтобы Express корректно видел HTTPS. TRUST_PROXY должен соответствовать реальному доверенному прокси, иначе IP-лимиты станут ненадёжными. Существующие polling/WebSocket upgrade не менять. По прежней защите V2.1 гостевой edge-handoff не переносит аккаунтный login между независимыми доменами: на резервном домене нужен отдельный вход; SSO не добавлялся.

Проверки после старта через согласованный hostname:

```sh
curl --fail --max-time 10 https://antikpoker.online/healthz
curl --fail --max-time 10 https://antikpoker.online/diagnostics -o /dev/null
curl --fail --max-time 10 'https://antikpoker.online/realtime/?EIO=4&transport=polling'
```

Админскую авторизацию, WebSocket upgrade и полноценную игру дополнительно проверить в браузере/diagnostics. Нельзя считать один healthz доказательством готовности игрового сервера.

## 9. Откат

Пока новые игры и аккаунты не разрешены после rollout: остановить сервис, вернуть сохранённый старый release и его зависимости (`npm ci`), прежний environment и согласованный backup БД/uploads, проверить SQLite integrity и запустить прежний сервис. Не заменять работающую WAL-базу по одному файлу: остановить процесс, сохранить текущее состояние отдельно и восстановить чистый runtime-каталог целиком.

Не выполнять DROP COLUMN, DELETE users или автоматическое «подтверждение всем». Если после выпуска уже прошли игры/регистрации, возврат старого backup потеряет новые данные: сначала сохранить текущее состояние и согласовать перенос/план восстановления. Автоматического destructive down-migration нет.
