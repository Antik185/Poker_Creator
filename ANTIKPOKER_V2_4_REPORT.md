# AntikPoker V2.4

Дата: 3 ноября 2026, Europe/Kaliningrad.
Статус: **LOCAL_READY — локально реализовано и проверено, production deployment НЕ выполнялся.**

Разработка выполнена в локальной ветке `codex/antikpoker-v2-auth`, поверх опубликованной V2.3 и её документации. Новый release candidate/архив для VPS пока не зафиксирован. Версия ресурсов сайта: `20261103d`.

## 1. Шапка и авторизация

Причина мигания: исходный HTML всегда показывал гостевой блок. `auth.js` заменял его только после `GET /api/auth/session`. Кроме того, обработчик сетевой ошибки ошибочно вызывал гостевое состояние.

- HTML шапки теперь формируется сервером по `userAuth.sessionFromRequest`: проверяются реальная HttpOnly-cookie, запись сессии, срок и отзыв. В шаблон передаются только экранированное имя и публичный URL аватара, не cookie, auth-токен или CSRF.
- Главная, комнаты, турниры, профиль и подтверждение email получают правильный исходный HTML. Для гостя сервер сразу показывает гостевые кнопки.
- Ошибка запроса сессии не означает logout: уже проверенная серверная шапка сохраняется. При восстановлении сети/возврате на страницу выполняется повторная проверка. Подтверждённое отсутствие сессии переключает интерфейс в гостевой режим.
- Logout немедленно рассылает существующее событие смены авторизации и обновляет шапку; запоздалый ответ загрузки аватара не восстанавливает старый аккаунт.
- Сохранена защита `sessionRevision`. Параллельные проверки сессии объединяются; устаревшие успешные ответы и ошибки не отменяют новый вход или выход.
- Блоку аккаунта зарезервирована ширина, длинный логин обрезается. Исправлен приоритет мобильного CSS, чтобы он не отменял `hidden` у ссылок авторизации.
- Пароли и auth-токены в localStorage не добавлялись. Исходное состояние не берётся из клиентского флага.

## 2. Автоматический аватар

- После выбора PNG/JPEG/WebP автоматически вызывается прежний защищённый `POST /api/profile/avatar`.
- Предпросмотр, форма подтверждения, «Сохранить», «Отмена», blob-URL и их обработчики/стили удалены.
- Камера, затемнение, меню, загрузка и удаление фото сохранены. Поверх аватара отображается индикатор; параллельные операции блокируются.
- До успешного ответа старый аватар не заменяется. Ошибка оставляет изображение и позволяет заново выбрать файл, включая тот же самый. Закрытие системного выбора ничего не меняет.
- Событие `antik:profile-updated` обновляет профиль и шапку. Игровые места обновляются прежним серверным `refreshAccountAvatar`; этот путь проверяется интеграционными тестами.
- Для обновления кэша используется существующий серверный URL с новым UUID и `?v=`. Способ хранения, WebP 256px, проверки содержимого, размера, CSRF, авторизации и лимиты не менялись.

## 3. Мобильная буква A

Только при ширине до 520px буква перенесена в верхний правый угол `auth-aside`. Сверху зарезервировано место под знак, на самых узких экранах он уменьшен. Текст не располагается под знаком. На планшете и desktop расположение информационного блока не изменено.

Дополнительно на ширине 320px устранено наложение кнопки регистрации на логотип в шапке.

## 4. Реальные турниры

Ранее `/tournaments` был демонстрационной заглушкой. Сейчас это рабочий каталог в существующем светло-синем стиле.

Источник данных:

- Администратор по-прежнему создаёт MTT через `POST /api/rooms`.
- Реальная сущность MTT определяется существующим условием: `config.launchMode === 'scheduled'` и корректный `scheduledStartAt`.
- Данные берутся из `rooms`, `tournament_registrations`, живого `TournamentManager` либо сохранённого `tournament_states`. Используется существующий `scheduledLobbyPayload`, без формирования подробных списков аватаров для каталога.
- Новый read-only `GET /api/tournaments` отдаёт ограниченную публичную проекцию и персональный статус участия по проверенной identity. Ответ `no-store`; чужие регистрации, email, секреты и управляющие identity не выдаются.
- Число участников — все реальные регистрации, а не только оставшиеся активные игроки. Время начала и лимит берутся из конфигурации, доступность регистрации — из существующих правил лобби.

Карточки показывают название, описание, статус, начало в часовом поясе браузера, число участников/лимит, регистрацию и действие. Сначала идут турниры с открытой регистрацией, затем остальные актуальные, затем завершённые. Для пустого списка: «Пока нет доступных турниров».

Каталог загружается при открытии и обновляется каждые 5 секунд, только когда страница видима. Есть кнопка обновления и повтор при восстановлении сети. При сетевой ошибке ранее загруженные карточки остаются. Неизменившийся список не перерисовывается.

Присоединение:

1. «Присоединиться» вызывает существующий `AntikGameEntry.ensure()`: аккаунт либо подтверждённый выбор гостя.
2. Клиент отправляет прежнее событие `registerTournament` через тот же `/realtime/`, polling с последующим WebSocket upgrade. Новый API регистрации не создавался.
3. Только после подтверждения участия сервером открывается существующее `/lobby/:code`.
4. Зарегистрированный активный участник видит «Перейти к турниру»; посадка/возвращение выполняются существующим механизмом лобби.
5. Заполненность, поздняя регистрация, повторное участие, выбывание, запрет guest для аккаунта и владение местом по-прежнему проверяются сервером. Завершённая карточка не предлагает регистрацию.

Скрипт Socket.IO загружается только при присоединении, с ограниченным временем ожидания. Зависимости каталога подключаются только на странице турниров. Обычные instant-комнаты в MTT не превращаются; их игровые ссылки и лобби сохранены. Раздел `/rooms` остаётся прежней заглушкой каталога комнат: его расширение не входило в V2.4.

**Создание MTT администратором и его появление в каталоге подтверждено интеграционным тестом. Присоединение непосредственно из карточки подтверждено и тестами, и браузером — отдельно аккаунтом и гостем. Дубликаты в SQLite не создаются.**

## 7. Миграции и безопасная будущая установка

**Новых миграций и зависимостей нет.** Используется существующая схема 1–3. Production SQLite, uploads, пользователи и результаты не использовались для тестов и не менялись. SSH/deployment, DNS, Cloudflare, Gcore и Nginx в этой работе не выполнялись/не менялись.

1. Зафиксировать проверенный V2.4 release candidate, собрать полный архив кода/шаблонов/ресурсов без SQLite, uploads, `.env` и `backups`; вычислить и проверить SHA-256. Не накладывать только frontend поверх старого renderer.

6. При серьёзной проблеме остановить выкладку. После проверки неизменности схемы откатить согласованный код/шаблоны/ресурсы на V2.3, **не восстанавливая старую SQLite поверх новых данных**. Восстановление БД с потерей новых записей требует отдельного разрешения.
